Streaming Windows audio to a HomePod

Apple doesn't make AirPlay senders for Windows, so I built one in Python: WASAPI loopback capture, a jitter buffer, an endless WAV stream and a reconnecting RAOP session through pyatv.

Macs and iPhones can send any audio to a HomePod with AirPlay. Windows can't, at least not out of the box. I wanted Spotify, YouTube, lecture videos, everything a Windows PC plays to come out of a HomePod mini, with one click and without installing a virtual audio driver.

HomePod Streamer is the result: a Python app with a CustomTkinter GUI, a tray icon and a CLI that captures whatever Windows is playing and streams it to the HomePod over AirPlay's RAOP protocol. This post walks through the audio pipeline and the reliability work that turned a demo into something that can run all day.

The pipeline

Capturing what Windows plays

WASAPI, the Windows audio API, has a loopback mode: you open an output device as if it were an input and receive a copy of everything being played through it. No virtual cable, no driver install. PyAudioWPatch exposes this from Python. The app captures in 20 ms periods and lets you choose any output device, or follow the system default.

Following the default turned out to be a feature people actually need. Plug in headphones and Windows switches the default output, so the loopback suddenly captures silence. A small monitor polls Windows Core Audio (through pycaw) every 1.5 s, and when the default changes, the capture switches to the new device without tearing down the AirPlay session. If the new device runs at a different sample rate, an ffmpeg resampler is inserted on the fly.

Turning a live capture into a "file"

pyatv, the excellent Python library I use for the AirPlay side, has a stream_file() method. It expects a file-like object it can read audio from, so the capture has to be presented as a readable WAV stream. Two problems showed up immediately.

Problem 1: a WAV file with no end

A WAV header declares the data length up front. For a live stream that length is unknown. The usual trick, writing 0xFFFFFFFF ("unknown"), made the decoder inside pyatv end the stream early, and so did 0. What does work is a very large finite size: 

# miniaudio ends the stream early with "unknown length" (0xFFFFFFFF) or 0;
# a very large finite value works (~6.2 hours at 48 kHz, then the stream restarts).
_WAV_DATA_SIZE = 0xFFFFFFF0 - 36

def wav_header(fmt: AudioFormat) -> bytes:
    """Build a PCM WAV header for a (practically) endless stream."""
    return (
        b"RIFF" + struct.pack("<I", _WAV_DATA_SIZE + 36) + b"WAVE"
        + b"fmt " + struct.pack("<IHHIIHH", 16, 1, fmt.channels, fmt.rate,
                                fmt.rate * fmt.frame_bytes, fmt.frame_bytes, fmt.sample_width * 8)
        + b"data" + struct.pack("<I", _WAV_DATA_SIZE)
    )

The trade-off is honest and documented: after roughly six hours the declared length runs out, and the stream restarts with a short gap.

Problem 2: silence is not "no data"

WASAPI loopback delivers nothing while Windows is not playing anything. But to pyatv, a read() that returns an empty bytes object means end-of-file, and the AirPlay session closes. So the stream must never return empty while it is alive. When the buffer is dry it returns zeroed PCM, which is silence.

A jitter buffer that never blocks

LiveWavStream sits between two threads: the capture thread calls push(), and pyatv's executor thread calls read(), pacing itself against real time and sometimes asking for just a few bytes. The core rules:

  • read() never blocks. It hands out whole frames when enough data is buffered, or silence otherwise.
  • Prebuffering after underruns. After the buffer runs dry, it keeps returning silence until prebuffer_ms (100 ms by default) has accumulated, so playback resumes smoothly instead of stuttering on every packet.
  • A latency cap. If the queue grows beyond max_buffer_ms (300 ms), it is trimmed back to the prebuffer level. Otherwise small clock drift between the capture device and the RAOP sender would slowly add delay forever.
  • Frame alignment. The ffmpeg pipe can deliver partial frames, so only whole frames are ever handed out. A half frame would shift every following sample and turn the audio into noise.
with self._lock:
    if self._prebuffering and len(self._buf) >= self._prebuffer_bytes:
        self._prebuffering = False
    # the ffmpeg pipe may deliver partial frames; only hand out whole frames
    n = min(want, len(self._buf) - len(self._buf) % fb)
    if not self._prebuffering and n:
        out = bytes(self._buf[:n])
        del self._buf[:n]
    else:
        if not self._prebuffering:
            self._prebuffering = True
            self.stats["underruns"] += 1
        out = bytes(want)          # zeroed PCM = silence
        self.stats["silence"] += want

The stream keeps statistics (bytes in and out, dropped, silence, underruns, peak level) that are logged every ten seconds. They made tuning easy: sent should match real time, underruns should be zero while music plays, and a peak of 0% means you are capturing the wrong output device.

Sample rates: 48 kHz in, 44.1 kHz out

Most Windows devices run at 48 kHz, while RAOP through pyatv always sends 44.1 kHz, 16-bit stereo. By default the conversion happens inside pyatv's decoder. If ffmpeg is on PATH, the app can instead pipe audio through ffmpeg's soxr resampler, which is noticeably cleaner on music. ffmpeg is deliberately not bundled, which keeps the standalone executable around 33 MB.

Reliability: the part that took longest

SituationDetectionBehaviour
Network drop or HomePod restartTCP probe to the AirPlay port every 2 s; two failures in a rowReconnect with backoff (1, 2, 4 … 30 s), rescanning from the second attempt in case the IP changed; volume is re-applied
An iPhone or Mac takes over the HomePodControl connection closed while the HomePod is still reachableStop with a message and don't reconnect, so two senders never fight over the speaker
Default output changesCore Audio poll every 1.5 sSwitch capture without interrupting the AirPlay session
Selected device disappearsCapture stream stopsFall back to the system default

The distinction in the second row matters most. "Connection lost" and "someone else took the speaker" look similar from the socket's point of view, but they need opposite reactions. The reachability probe tells them apart: if the HomePod still answers on its AirPlay port, the session was closed on purpose.

Reconnecting is also only enabled after audio has flowed at least once. If the very first connection fails, usually because of the firewall, the app shows the error instead of retrying forever.

One stream per machine

The GUI and the CLI can both start a stream, and two senders connected to the same HomePod can leave one of them as a silent "zombie" that keeps the speaker busy. A Windows named mutex (Local\HomePodStreamer.Stream) now guarantees a single stream per machine, and Windows releases it automatically if the process dies.

The Windows-specific details

  • Firewall per program path. During AirPlay 2 setup the HomePod connects back to the PC. Windows Firewall stores permissions per executable, so python.exe might be allowed while pythonw.exe (the GUI) is blocked. The app detects the missing rule and offers an Allow button that adds a local-network-only rule after a UAC prompt.
  • Start with Windows uses a per-user HKCU\…\Run entry, so no admin rights are needed. Combined with "start streaming when the app opens", the PC streams to the last speaker right after sign-in. If the speaker isn't reachable yet, it rescans up to six times, ten seconds apart, and never silently switches to a different speaker.
  • Tray first. Closing the window keeps the app in the tray, with a colored status dot (green streaming, orange reconnecting, red error), a volume menu and Windows notifications for drops and reconnects. Launching it again brings the existing window forward instead of starting a second copy.
  • Single-file build. PyInstaller produces one .exe; settings and logs move to %APPDATA%\HomePod Streamer\ when running frozen.

Code structure

The asyncio engine runs on a background thread (controller.py) and talks to the Tkinter UI through an event queue, so the GUI never blocks on network calls. The rest is split by responsibility: discovery.py (mDNS), capture.py (WASAPI and resampling), streamer.py (jitter buffer and the RAOP session), gui.py, tray.py, firewall.py and autostart.py. pyatv is pinned to 0.18.0 because the session watchdog reads an internal field; if a future version removes it, the watchdog disables itself instead of crashing.

Limitations

  • About two seconds of latency. That is inherent to AirPlay buffering. It is perfect for music and podcasts and unsuitable for video or games.
  • Audio plays from the PC and the HomePod, because loopback copies a device that is still playing.
  • The HomePod must allow access to "Everyone on the Same Network" without a password in the Home app.

This project taught me a lot about real-time audio: buffers, clocks, frame alignment and the many ways a network connection can end. Most of the work was not streaming itself but making it survive everything around it.
