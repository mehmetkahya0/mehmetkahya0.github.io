A 140-line scraper, and what I'd fix today

Web Resource Downloader grabs images, scripts and media from a website with requests and BeautifulSoup. A walkthrough of how it works, plus an honest code review of my own older code.

Web Resource Downloader is a small Python command-line tool: give it a URL and a folder, and it downloads the resources the page references (images, scripts, media), then follows the same-site links on that page and does the same there. It has more than 20 stars, and its code fits on one screen.

Small projects are great teaching material because you can see the whole thing at once. This post walks through how it works, then does something I think more developers should do in public: an honest review of my own older code, with the fixes I would make today.

Usage

python main.py https://example.com ./downloads --extensions png jpg js --log run.log
  • url and folder are required positional arguments.
  • --extensions limits downloads to the given file types.
  • --log mirrors the results into a log file.
  • --delete removes the folder after the run, which is handy for measuring a site without keeping the files.

Each run prints a table of what happened to every resource (downloaded, skipped or failed, with a timestamp) and writes it to output.txt and, as Markdown, to output.md, so the results can be pasted into an issue or a report.

How it works

The whole program is four small functions and a main():

  1. get_html(url) fetches the page with requests and fails loudly on HTTP errors.
  2. get_links(html, base_url) collects every <a href>, resolves it to an absolute URL and keeps only links on the same host, so the crawl never wanders off to other sites.
  3. get_resources(html, base_url, args) finds every element with a src attribute (images, scripts, video, audio, iframes) and keeps those whose extension matches the filter.
  4. download_resources(folder, resources) streams each file to disk in 8 KB chunks and records the result in a PrettyTable.
def get_links(html, base_url):
    soup = BeautifulSoup(html, 'html.parser')
    links = set()
    for link in soup.find_all('a', href=True):
        url = convert_to_absolute_url(link['href'], base_url)
        if '://' in url and urllib.parse.urlparse(base_url).netloc != urllib.parse.urlparse(url).netloc:
            continue
        links.add(url)
    return links

Two choices hold up well. urljoin handles every relative-URL shape correctly (img.png, /img.png, ../img.png, //cdn.host/img.png), which hand-written string concatenation always gets wrong somewhere. Streaming with iter_content keeps memory flat even for large videos, because a file is never held in memory as a whole.

A code review of my own code

Reading this code again with more experience, I see several things I would change. None of them are exotic; they are the kind of issues that show up in most first versions of a scraper, which is why they are worth listing.

1. The default filter downloads nothing

The help text says "if not provided, all resources will be downloaded", but --extensions defaults to an empty list, and the filter is a plain membership test: 

if url.split('.')[-1] in args.extensions:   # always False when the list is empty
    resources.append(url)

The fix is one condition: if not args.extensions or ext in args.extensions. While at it, the extension should come from urlparse(url).path, because image.png?v=3 currently produces the "extension" png?v=3.

2. Stylesheets are never found

Resources are collected from src attributes only, but stylesheets are referenced with <link rel="stylesheet" href>, and responsive images often live in srcset. A complete version would also read link[href], srcset candidates and url() references inside the downloaded CSS.

3. Filenames can collide, or escape the folder

The local filename is the last path segment of the URL. Two different /a/logo.png and /b/logo.png files overwrite each other, and a URL ending in a slash yields an empty name. Mirroring the URL path inside the target folder, after normalizing it and rejecting .. segments, fixes both problems and keeps every write safely inside the chosen directory.

4. One session, timeouts and politeness

  • Every request opens a new connection. A shared requests.Session() reuses connections and is much faster for many small files.
  • There is no timeout=, so one hanging server stalls the whole run.
  • A well-behaved crawler sends a descriptive User-Agent, respects robots.txt and adds a small delay between requests.
  • The same resource referenced on several pages is downloaded again each time. A seen set would avoid that.

5. Errors should not kill the crawl

get_html() calls sys.exit(1) on any request error. That is right for the starting URL, but when following links, one broken page ends the entire run. Returning None and logging the failure would let the crawl continue.

What a rewrite would look like

session = requests.Session()
session.headers["User-Agent"] = "WebResourceDownloader/2.0 (+github.com/mehmetkahya0)"

def wanted(url: str, exts: set[str]) -> bool:
    ext = Path(urlparse(url).path).suffix.lstrip(".").lower()
    return not exts or ext in exts

def local_path(folder: Path, url: str) -> Path:
    rel = Path(unquote(urlparse(url).path.lstrip("/")) or "index")
    target = (folder / rel).resolve()
    if folder.resolve() not in target.parents:
        raise ValueError(f"unsafe path: {url}")
    return target

Add concurrency with a small thread pool (downloads are I/O-bound, so threads work well here) and a progress bar, and the tool would go from "works on my test page" to something you can point at real sites.

Why write this post

It would have been easy to only write about my newest, most polished projects. But looking back at older code and naming what you would do differently is one of the clearest ways to see how much you have grown. This little tool taught me URL resolution, streaming downloads and argument parsing. Revisiting it reminded me that edge cases, not happy paths, are where most of the engineering lives.
