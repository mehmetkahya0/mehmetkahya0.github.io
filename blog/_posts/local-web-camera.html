Local Web Camera answers a simple wish: point an old phone or laptop at something and watch it from another device in the house, with no app store, no account and no cloud service in between. Open a page on the device with the camera, share a link, open it on the viewer, done.

Building it means understanding how WebRTC really fits together. This post covers how signaling, ICE and the media path fit together, and then, honestly, what I would change if I wrote it again today.

The big picture

WebRTC sends video directly between browsers, but browsers can't find each other on their own. They need a signaling channel to exchange two kinds of messages: session descriptions (SDP offers and answers that describe codecs and media) and ICE candidates (possible network addresses to reach each other). WebRTC deliberately doesn't specify how signaling works, so you bring your own. Here it is Socket.IO on a small Express server.

Rooms and signaling

The server keeps an in-memory map of rooms. Each room maps socket ids to a small record that includes which streams a peer has started. When someone joins, existing members hear about the newcomer, and the newcomer receives the list of existing users: 

socket.on('join-room', (roomId) => {
  if (!rooms.has(roomId)) rooms.set(roomId, new Map());
  const room = rooms.get(roomId);
  room.set(socket.id, { peerId: socket.id, streams: new Set() });
  socket.join(roomId);

  socket.to(roomId).emit('user-connected', socket.id);
  socket.emit('existing-users', Array.from(room.keys()).filter(id => id !== socket.id));
});

// SDP and ICE are relayed untouched to the other peers in the room
socket.on('offer', (offer, roomId) => socket.to(roomId).emit('offer', offer));
socket.on('answer', (answer, roomId) => socket.to(roomId).emit('answer', answer));
socket.on('ice-candidate', (c, roomId) => socket.to(roomId).emit('ice-candidate', c));

The server never inspects media and never stores anything. On disconnect it tells the room that the peer's streams stopped, removes the peer, and deletes the room when it becomes empty. There is also a tiny admin "console" over the same socket that can list rooms and users or clear everything, which is handy when debugging connections.

A host creates a room with a random id and shares a link of the form http://<host-ip>:8080?room=<id>. The viewer page reads room from URLSearchParams and joins automatically. To help with that link, the server walks os.networkInterfaces(), picks the first non-internal IPv4 address and exposes it at /config.

The media path

The host requests the camera with constraints that prefer HD but accept less on weaker devices:

localStream = await navigator.mediaDevices.getUserMedia({
  video: {
    width: { ideal: 1280, max: 1920 },
    frameRate: { ideal: 30, max: 60 },
    facingMode: 'user'
  },
  audio: true
});

Using ideal rather than exact is the important part. exact constraints make getUserMedia fail outright on a camera that can't meet them, while ideal lets the browser get as close as it can.

ICE: finding a path

On a home network the two devices can usually reach each other directly through their local addresses ("host" candidates), so the video never leaves the LAN. The peer connection is still configured with several public STUN servers and a TURN server, so a connection can be established across trickier NATs too. STUN lets a device discover its public address; TURN relays the media when no direct path exists.

The app listens to iceConnectionState and connectionState, prints a timestamped connection log in the UI, and treats failed or disconnected as a cue to attempt a reconnect. On the signaling side, the Socket.IO client is configured with automatic reconnection (five attempts) and generous ping timeouts, so a phone that briefly drops Wi-Fi recovers on its own.

Seeing what the connection is doing

"The video is choppy" is not a bug report you can act on. So both the host and viewer pages poll RTCPeerConnection.getStats() and plot live charts with Chart.js: frames per second, bytes received (bitrate) and packets lost, over a sliding window of data points. Charts update with update('none') to skip animations, so drawing them doesn't compete with video decoding. A rising packet-loss line is usually the first sign of weak Wi-Fi.

What I would change today

Rereading the code with fresh eyes, there are things I would do differently. They are worth writing down because they are common mistakes:

  • Serve a public/ folder, not the project root. The server uses express.static(__dirname), which makes every file in the project downloadable, including server.js and the TLS key. Static serving should be limited to a dedicated folder of client files.
  • Never commit private keys or node_modules. A self-signed key for local development should be generated on first run, for example with mkcert, and listed in .gitignore. Dependencies belong in package-lock.json, not in the repository.
  • Secure contexts. Browsers only allow getUserMedia on HTTPS or localhost. Serving over HTTPS on the LAN would let any device be the camera, not just the one running the server.
  • Address messages to a peer. Offers and answers are broadcast to the whole room today, which works for one viewer. Sending them to a specific socket id would make several viewers per room possible.
  • Unguessable room ids and an origin allow-list. Math.random() ids and a wildcard CORS policy are fine on a trusted home network, but crypto.randomUUID() and a restricted origin cost nothing.

What I learned

WebRTC looks intimidating because it bundles many protocols (SDP, ICE, STUN, TURN, DTLS, SRTP), but the mental model is small: exchange descriptions, exchange candidates, let the browsers do the rest. Once that clicked, the remaining work was ordinary engineering: reconnects, state handling and visibility into what the connection is actually doing.
