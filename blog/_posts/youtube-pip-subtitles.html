Picture-in-Picture is perfect for keeping a lecture or a talk on screen while you work. The annoying part: the moment a YouTube video pops out, the subtitles vanish. They stay behind on the main page, rendered on top of a player you can no longer see. For non-native speakers, or anyone in a noisy room, that makes PiP almost useless.

YouTube PiP Subtitles is a small Manifest V3 extension that fixes this. It opens a Picture-in-Picture window that contains both the video and a subtitle overlay kept in sync with playback, styled however you like. This post explains why the obvious fixes don't work and what the extension does instead.

Why captions disappear in PiP

YouTube does not burn captions into the video stream. It renders them as HTML elements (.ytp-caption-segment and friends) positioned over the <video> element. The classic video.requestPictureInPicture() API only takes the raw video element and gives you a floating window that can show nothing else: no HTML, no overlays, no styling. So whatever lives in the DOM around the video, captions included, stays on the page.

Any real fix therefore needs a PiP window that can render arbitrary HTML. Chrome 116 added exactly that: Document Picture-in-Picture. documentPictureInPicture.requestWindow() opens an always-on-top window with its own document, which you can fill like any page.

The pipeline

Getting the caption data

YouTube's player response lists the available caption tracks under captions.playerCaptionsTracklistRenderer.captionTracks, each with a baseUrl pointing to the timedtext endpoint. The extension picks a track (Turkish first, then English, then whatever is available) and asks for the JSON3 format by appending &fmt=json3. JSON3 gives millisecond timings per event, which makes parsing almost trivial: 

function parseCaptionJSON3(data) {
  if (!data?.events) return [];
  return data.events
    .filter(ev => ev.segs && ev.tStartMs !== undefined)
    .map(ev => ({
      start: ev.tStartMs / 1000,
      end:   (ev.tStartMs + (ev.dDurationMs || 3000)) / 1000,
      text:  ev.segs.map(s => s.utf8 || '').join('').trim(),
    }))
    .filter(ev => ev.text && ev.text !== '\n');
}

The dDurationMs || 3000 fallback covers events that come without a duration, which happens with some auto-generated tracks.

Opening the window

The PiP window is sized from the video's real aspect ratio (480 px wide), then filled with a wrapper, the video and an overlay element for the subtitles. Putting the video into a different document is the delicate part, and the extension tries two strategies:

  1. captureStream() on the page's video, fed into a new muted <video> inside the PiP window. The original element stays where YouTube expects it.
  2. If that fails or yields no video track, which happens on many videos because of CORS and DRM restrictions, the real <video> element is moved into the PiP document. Its original parent and sibling are remembered so it can be put back exactly where it was when the window closes (pagehide).

Keeping text in sync

Sync is a 100 ms interval that reads currentTime and renders every cue whose window contains it. Overlapping cues are joined, and the DOM is only touched when the text actually changes. Slightly simplified from content.js: 

syncInterval = setInterval(() => {
  const vid = streamOk ? video : (win.document?.querySelector('video') || video);
  const t = vid.currentTime;
  let text = '';

  if (captionData.length > 0) {
    const matches = captionData.filter(c => t >= c.start && t < c.end);
    text = matches.map(c => c.text).join(' ').trim();
  }
  if (!text) text = getDOMCaptions();   // fallback: YouTube's own caption DOM

  if (text === lastText) return;
  lastText = text;
  pipSubEl.innerHTML = text ? renderLines(text) : '';   // lines are HTML-escaped
}, 100);

Why setInterval and not requestAnimationFrame? rAF is throttled or paused when a document is not visible or focused, and the whole point of PiP is that the main tab is usually in the background. A plain interval keeps polling steadily, and 100 ms is well below the threshold where a subtitle feels late.

Every line goes through an HTML-escaping helper before it is inserted. Caption text is third-party data, and innerHTML with unescaped text from the network is a classic XSS hole.

The DOM fallback

When there is no prefetched cue data, the extension reads YouTube's visible caption elements instead. It tries a few selectors (.ytp-caption-segment, .captions-text, [class*="caption-visual-line"]) and keeps only elements that are actually visible according to getComputedStyle. That is why you should switch captions on with YouTube's own CC button first: the fallback can only mirror what the player is rendering.

Living inside a single-page app

YouTube never does a full page load when you click another video, so DOMContentLoaded fires once and never again. The extension watches for URL changes with a MutationObserver on document.body. When the URL changes it resets the cue data and the selected track, then re-runs initialization after a short delay so the new player has time to mount. The buttons (one in the player's toolbar next to the native PiP button and one floating "PiP + Subtitles" button that appears on hover) are injected with retry loops for the same reason: the controls may not exist yet when the script runs.

Customization that applies live

The popup lets you set font size (10–32 px), font family, text color, background opacity and position (top or bottom). Settings are stored in chrome.storage.sync, so they follow you across devices, and a chrome.storage.onChanged listener restyles the open PiP window immediately, with no reopen needed.

Permissions and privacy

The manifest asks for very little: the storage permission and a content script on youtube.com. The only other host it talks to is my GoatCounter instance, which receives anonymous page-path pings such as "extension active" and "PiP opened" so I can see whether the feature is used. No video data, captions or personal data leave the browser.

What I would improve next

Writing this post made me look at the code with fresh eyes, and a few improvements stand out:

  • Reading the player response from the page's world. Content scripts run in an isolated JavaScript world, so page globals such as ytInitialPlayerResponse are usually not visible to them. In practice the DOM fallback carries a lot of the work today. MV3 supports injecting a script into the page's main world (world: "MAIN"), which could hand the track list back reliably.
  • A track picker. The language preference is fixed today; the popup could list every available track, including auto-translations.
  • Binary search for cues. Filtering the whole cue array ten times per second is fine for normal videos, but a sorted array plus binary search would make multi-hour streams cheaper.

The extension needs Chrome or Edge 116+, since Firefox and Safari don't ship Document PiP yet. It is a good example of a pattern I keep coming back to: when the platform won't let you move the UI, move the data and render it yourself.
