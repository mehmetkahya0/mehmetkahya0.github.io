AI Catalog is the most-starred repository on my profile: close to 500 stars and more than 120 forks at the time of writing. It is a curated list of AI models, tools and platforms, more than 500 entries across over 40 categories, from text-to-image generators and LLMs to SQL assistants, voice cloning and autonomous agents.

A curated list sounds like the least technical project imaginable. In practice, keeping hundreds of entries consistent, reviewable and actually usable turned into an interesting engineering problem. This post covers the format, the tooling around it, and the website that turns the README into a searchable catalog without a single build step.

One file as the source of truth

The whole catalog lives in README.md. That was a deliberate choice: GitHub renders it, people can star and fork it, and contributors only need to know Markdown to open a pull request. Every entry follows the same shape: 

- **[Tool name](https://tool.url)** 🆓🔄 - One short line describing what it does

The emoji after the link are a small but very effective schema. They encode pricing and status at a glance:

MarkerMeaning
🆓Completely free
💰Paid (subscription or one-time)
🔄Freemium: free tier with paid upgrades
🆕Recently added
🔥Popular, highly recommended by the community

Categories are ## headings; finer groupings use ### and ####. The LLM section, for example, splits into commercial models, open-source models, self-hosted solutions and research projects. A short > blockquote under a heading can describe the category.

Tooling that keeps the list honest

The bigger a list gets, the more it drifts: duplicated entries, missing pricing markers, descriptions that turn into paragraphs. The repository ships three small shell scripts to fight that drift.

  • scripts/add-tool.sh asks for the name, URL, description and pricing type, then prints a correctly formatted line. Contributors copy it instead of hand-formatting.
  • scripts/validate.sh is a quality gate built from grep and awk. It flags malformed entries, tools without a pricing marker, descriptions over 100 characters, and duplicate names.
  • scripts/stats.sh counts tools and categories for the "Quick stats" section.
# Check for missing pricing indicators
tools_without_pricing=$(grep -n "^\s*-\s*\*\*\[.*\].*\*\*\s*-" README.md | grep -v "🆓\|💰\|🔄\|🆕\|🔥")

# Check for duplicate entries
duplicates=$(grep -o "\*\*\[.*\]" README.md | sort | uniq -d)

Around the scripts sits the usual open-source scaffolding, which matters a lot once strangers start contributing: issue templates for bug reports, feature requests and tool submissions, a pull-request template, a contributing guide, a code of conduct and a roadmap. The tool-submission template alone saves a lot of back-and-forth, because it asks for exactly the fields an entry needs.

The website: parsing the README at runtime

A 500-entry Markdown file is great to browse on GitHub and painful to search. So the repository also contains a single index.html, served on GitHub Pages, that turns the README into a fast, filterable catalog. The key design decision: no generated data file. The page fetches the README itself and parses it in the browser, so the site can never go stale. Merge a pull request and the website is updated. 

const SOURCES = ['README.md', 'https://raw.githubusercontent.com/mehmetkahya0/AI-Catalog/main/README.md'];

It tries the README served next to the page first and falls back to the raw GitHub URL, so the same file works on Pages and when opened from a fork.

A line-by-line parser

The parser walks the Markdown one line at a time and keeps a little state: the current category, the current sub-group and an optional description. A few rules carry most of the weight:

  • Headings like "Table of contents", "Contributing" or "License" are skipped with one regular expression, so only real categories become filters.
  • ### headings that start with a letter (for example "Summarizer") are categories of their own, while emoji-led ones ("🔥 Commercial LLMs") are treated as sub-groups inside their parent. Unicode property escapes (\p{L}) make that distinction a single test.
  • Each list item is matched against the entry pattern. The emoji block becomes boolean flags (free, freemium, paid, isNew, hot), and the text after - becomes the description.
if ((m = item.match(/^\*{0,2}\[([^\]]+)\]\(([^)\s]+)\)\*{0,2}\s*(.*)$/))) [, name, url, rest] = m;

Search, filters and small touches

The UI combines a category sidebar (a select on mobile), a search box and pricing/status filter chips. Search matches the name, description, category, sub-group and URL, and highlights matches with <mark>. The query is regex-escaped first, so typing c++ doesn't throw. Every string from the README is HTML-escaped before rendering, since contributors control that content.

Each card shows the tool's favicon (fetched from Google's favicon service and removed silently if it fails), the host name and its badges. Entries without a URL fall back to a web search for the tool's name. A light/dark theme toggle remembers your choice in localStorage, wrapped in try/catch for browsers that block storage.

What maintaining it taught me

  • Curation is the product. Adding tools is easy; deciding what not to add, and pruning tools that died, is what keeps a list worth starring.
  • Make the right thing the easy thing. A formatter script and a submission template did more for consistency than any amount of review comments.
  • Keep data and presentation in one place. Parsing the README at runtime means there is exactly one thing to update, which is the main reason the website has never drifted from the list.

What is next

The obvious next step is automation: a GitHub Action that runs validate.sh on every pull request and a scheduled job that checks links for dead tools. The validator is already script-shaped, so wiring it into CI is mostly configuration.

If you know a tool that belongs in the catalog, the submission template is the fastest way in, and a star helps more people find it.
