Long Claude Code tasks rarely come as one prompt. They come as a sequence: plan → implement → run the tests → review with fresh eyes → write the changelog. Each step only makes sense after the previous one has finished, which means somebody has to sit at the terminal, wait for the turn to end and type the next prompt.

Chain Prompt removes that babysitting. You queue the whole sequence, pick a folder and press Start. The app runs the real interactive claude inside a real pseudo-terminal, types each prompt the moment the previous turn finishes, and pings you when the chain is done, when Claude needs a permission, or when something goes wrong. This post is about how it knows a step is finished, because that turned out to be the whole project.

The problem with watching the terminal

The obvious approach is screen scraping: read the terminal output, wait until the spinner disappears and the input box comes back, then send the next prompt. I rejected it early. Claude Code's TUI redraws constantly, the exact strings change between versions, and a regex that matches "the turn is over" will eventually match in the middle of a turn too. An automation tool that sends a prompt at the wrong moment is worse than no tool at all.

Claude Code already has a reliable signal for this: hooks. When a turn ends it fires Stop; when you submit a prompt it fires UserPromptSubmit; when it waits for a permission it fires Notification. If the app can receive those events, it never has to guess.

Architecture at a glance

The app is Electron with a deliberately small surface:

  • Main process: a loopback HTTP HookServer, a SessionManager that owns one node-pty running claude, and the ChainRunner state machine.
  • Renderer: vanilla TypeScript for the queue UI plus xterm.js with the fit addon, so the terminal is a real terminal you can type into, scroll and copy from.
  • Preload: a narrow, typed API between the two. The renderer runs with contextIsolation, sandbox: true, no Node integration and a strict CSP.

Injecting hooks without touching your settings

I did not want to edit anyone's ~/.claude/settings.json. Claude Code accepts a --settings <file> flag, and hooks from that file are merged with the user's and the project's hooks rather than replacing them. So every launch gets its own temporary settings file in the OS temp directory, written with mode 0600 and deleted when the session ends.

Each hook is a small curl command that forwards the hook's JSON input (which arrives on stdin) to the app:

// curl fallback: the hook input arrives on stdin and is forwarded as the body.
// Only double quotes are used so the line works in sh, cmd and PowerShell;
// on Windows `curl.exe` avoids PowerShell's `curl` alias.
const curl = (opts.platform ?? process.platform) === 'win32' ? 'curl.exe' : 'curl'
const command =
  `${curl} -s -m 5 -X POST -H "content-type: application/json" ` +
  `-H "${TOKEN_HEADER}: ${opts.token}" --data-binary "@-" "${url}"`
return { type: 'command', command, timeout: 10 }

Claude Code also supports native type: "http" hooks, and the app can use them. While checking against --debug output I found that HTTP hooks are not supported for SessionStart and SessionEnd, so those two always fall back to curl. Small detail, but without it the app would never learn that claude is ready.

A loopback server that only trusts its own sessions

The HookServer binds to 127.0.0.1 on port 0, so the OS picks a free port. Every request must carry a random 24-byte token generated per app run, compared in constant time; anything else gets a 403. The URL encodes which launch the event came from: 

POST http://127.0.0.1:<port>/hook/<launchId>/<EventName>

That launchId matters more than it looks. When the app restarts claude (for a fresh context, say), the old process can still deliver a late SessionEnd. Because every launch has its own id, stragglers from a killed session are simply ignored. The server also always answers with an empty 2xx, which Claude Code reads as "success, no decision": the app only observes and never influences what Claude does.

The chain state machine

ChainRunner turns hook events into step transitions. The rules sound simple, but each one fixes a real failure mode I ran into:

EventMeaning for the chain
UserPromptSubmitOur prompt was accepted. Until this arrives, the step is not really running.
StopThe step is done; schedule the next one after a configurable delay.
NotificationIf the type is a permission or input prompt, the step switches to Needs you and you get a notification.
PostToolUseClaude is working again after you answered, so go back to Running.
StopFailureAn API error. The step fails and the chain pauses on it.
SessionEnd / pty exitThe session died mid-step. Fail and pause.

The most important guard is a single boolean. A Stop that arrives before our prompt was accepted belongs to an earlier turn, and treating it as "done" would skip a step instantly: 

case 'Stop':
  // A Stop before our prompt was accepted belongs to an earlier turn.
  if (this.submitted) this.completeStep(step, String(p.last_assistant_message ?? ''))
  break

Async sequences such as "start claude, wait until ready, send /clear, wait again, paste the prompt" can be cancelled halfway by Pause or Stop. Instead of threading abort signals through everything, the runner keeps a generation counter. Every command bumps gen, and every await point checks g !== this.gen before continuing. It is a cheap, very effective way to make stale continuations harmless.

Typing into a TUI reliably

Sending a multi-line prompt to an interactive program is surprisingly easy to get wrong: the first newline submits the prompt early. The fix is bracketed paste. The prompt is wrapped in ESC[200~ … ESC[201~, so the TUI treats it as one pasted block, and Enter is sent separately after a short delay that scales with the prompt length: 

pastePrompt(text: string): void {
  const body = text.replace(/\r\n/g, '\n').replace(/\x1b\[20[01]~/g, '')
  this.write(`\x1b[200~${body}\x1b[201~`)
}

// later, in the runner:
session.pastePrompt(step.prompt)
await sleep(Math.min(3000, 400 + Math.floor(step.prompt.length / 20)))
session.pressEnter()

If no UserPromptSubmit arrives within 8 seconds, Enter is sent once more; if that also fails, the step is marked as failed with a message that points at the likely cause (curl missing, hooks disabled, or an allowedHttpHookUrls list blocking HTTP hooks).

"Ready" is a hook plus a quiet terminal

SessionStart fires slightly before the TUI has finished drawing its input box. So "ready" means a SessionStart newer than the last action has arrived and the terminal has been quiet for 700 ms. The same logic handles /clear, which fires SessionEnd followed by SessionStart with source: clear. That is exactly the signal for "the fresh context is ready".

Things I had to verify, not assume

  • Folder trust. Claude asks "Do you trust this folder?" in a new directory, defaulting to No, exit, and SessionStart only fires after you confirm. The app never answers that dialog for you; after 20 seconds it notifies you to confirm in the terminal, and the chain starts by itself afterwards.
  • Nested sessions. If you launch the app from inside a Claude Code session, variables like CLAUDECODE and CLAUDE_CODE_* leak into the child, which then behaves like a nested session. They are stripped from the pty environment.
  • Shells per OS. On Windows claude runs through powershell.exe -NoExit, which resolves .exe, .cmd and .ps1 shims. On macOS and Linux it runs through $SHELL -i -l -c so .zshrc / .profile PATH additions apply, then drops into a normal shell so the terminal stays usable.
  • Locale on macOS. Apps opened from Finder get no LANG, which made claude's UI fall back to ASCII. The app sets en_US.UTF-8 when nothing is set, like Terminal.app does.

Built for unattended runs

The point of a chain is to walk away, so failure handling matters as much as the happy path. API errors, a claude exit, an unaccepted prompt or a stall (no terminal output for N minutes) all pause the chain on the exact step and notify you, on the desktop and optionally on your phone via ntfy. Electron's powerSaveBlocker keeps the machine awake while a chain runs. The queue is persisted, and a step that was running when the app closed reopens as Interrupted, so you can resume from it.

Every run writes a human-readable .log and a machine-readable .json into <folder>/.chain-prompt/logs/, with a .gitignore so logs never end up in your repository. Chains themselves are plain JSON templates: 

{
  "format": "chain-prompt",
  "version": 1,
  "name": "feature-workflow",
  "steps": [
    { "prompt": "Read the codebase and write a short implementation plan for TODO.md to PLAN.md." },
    { "prompt": "Implement the plan in PLAN.md step by step." },
    { "prompt": "Run the test suite and fix every failing test you introduced." },
    { "prompt": "Review the diff with fresh eyes and fix what you find.", "newSession": true }
  ]
}

How I test something that drives an AI

There are three layers, each proving something the others cannot:

SuiteNeeds claudeWhat it proves
test:unitNo30 state-machine checks: chaining on Stop, ignoring a stale Stop, permission → Needs you → running, pause/resume, Esc to stop, stall auto-pause, restore as Interrupted.
test:chainYesA real 3-step chain without Electron: multi-line prompts arrive intact, steps run in order, logs are written.
test:e2eYesDrives the packaged Electron app with Playwright, then quits mid-step and relaunches to check the step comes back as Interrupted.

My favorite test is the third step of test:chain. Step 1 asks Claude to reply with exactly ALPHA; step 3 starts with a fresh context and asks which word it was told to reply with first. The expected answer is UNKNOWN, which proves that /clear really reset the context instead of just looking like it did.

Limitations and what is next

  • If Claude asks you a question and ends its turn, that is also a Stop, so the next prompt is sent. For unattended chains, tell Claude in the prompt to make reasonable assumptions instead of asking.
  • One folder and one session at a time. Running several chains in parallel is the obvious next feature.
  • Public ntfy topics are readable by anyone who knows the name, so choose an unguessable one.

The biggest lesson was to trust the tool's own lifecycle events over anything you can see on screen. Once the app stopped guessing and started listening, the rest became ordinary state-machine engineering. Builds for Windows and macOS (Apple Silicon and Intel) are on the GitHub releases page.
